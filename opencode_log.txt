### Problem
User reported two issues while monitoring live RTTY with fldigi:
1. Waterfall not displaying actual audio spectrum from fldigi

### Investigation

#### Environment discovery

  - `alsa_input.pci...analog-stereo` (SUSPENDED)

#### Root cause #1: RX Text
- Code was tailing `~/.neodigi-fldigi/fldigi.log` using `QFileSystemWatcher`
- **File does not exist** — fldigi does NOT write decoded received text to disk by default
- `fldigi.prefs` has `log_enabled:0` (controls ADIF logbook, not relevant to decoded text)
- No `fldigi.log` anywhere in `~/.neodigi-fldigi/`
- The design in `CLAUDE.md` §14 says "NEVER call text.get_rx — crashes fldigi, confirmed bug"
  - However, confirmed by inspecting fldigi 4.2.11 source (`src/network/xmlrpc.cxx:3721`) that **`rx.get_data`** exists and is safe:
    - Signature: `"6:n"` (returns byte string, no params)
    - Returns all RX data received since last query
    - Mutex-protected (`rx_data_mutex`) via `get_rx_data()` in `src/dialogs/fl_digi.cxx:8122`
    - Buffer is cleared after each read (get-and-clear semantics)
    - Uses `REQ_SYNC` for FLTK main thread safety

#### Root cause #2: Waterfall
- `WaterfallWidget` defaults to `m_stubMode = true`
- 3-second timer in `MainWindow` calls `setAudioDevice(-1)` → `initAudio(nullptr)`
- `pa_simple_new(nullptr, ...)` connects to PulseAudio/PipeWire **default source**
- If the default source is SUSPENDED or not receiving radio audio, the waterfall gets silence
- **No visual feedback** when audio init fails — silently falls back to stub mode with fake noise
- `initAudio` also had a resource leak: FFTW allocated before PA init, leaked if PA failed

## Session 2: Re-entrancy Bug + Waterfall Source Selection (2026-05-10)

### Problem (User confirmed first fix didn't work)
Both issues persisted after first round of fixes. User also asked: *"is the waterfall display tied to the audio capture device, not the playback device?"*
  - **Answer:** Yes — waterfall reads from an **input/capture device** (`PA_STREAM_RECORD`), the same audio source fldigi uses for decoding (radio audio → computer line-in). This is correct for a waterfall.

### Investigation — Two new bugs found

#### Bug 1: RX Text — Re-entrancy guard drops `rx.get_data`
- `m_rxDataTimer` was set to fire every **250ms** independently of the main poll timer
- `FLDigiClient::call()` has a **re-entrancy guard**: drops any call if another is in-flight:
  ```cpp
  if (m_callInProgress) {
      qDebug("[XMLRPC] ⚠ dropped (previous call still pending): %s", ...);
      return {};
  }
  ```
- The main poll timer (`onPollTimer`, 500ms single-shot) makes **17+ sequential XML-RPC calls**, each blocking via QEventLoop
- The 250ms RX timer almost always fired DURING a poll cycle → `rx.get_data` silently dropped
- **Fix:** Merge `rx.get_data` into the main `onPollTimer()` cycle. Remove separate `m_rxDataTimer`.

#### Bug 2: Waterfall — `pa_simple_new(nullptr)` succeeds on SUSPENDED source
- Previous fix had a two-attempt fallback:
  - Attempt 0: system default (nullptr)
  - Attempt 1: RUNNING source (only if attempt 0 failed)
- **Problem:** `pa_simple_new(nullptr, ...)` **succeeds** even on SUSPENDED sources — PulseAudio/PipeWire auto-activates them and returns a "working" stream that yields silence
- So attempt 0 always succeeded, and the RUNNING-source fallback (attempt 1) NEVER executed
- The waterfall silently connected to the wrong source (e.g., motherboard audio or HDMI monitor) with no error
- **Fix:** When `sourceName` is nullptr (auto-detect), build a candidate list:
  1. RUNNING capture sources first (likely fldigi's device)
  2. SUSPENDED capture sources next
  3. System default (nullptr) as last resort
  - Iterate until one succeeds

     - RUNNING sources first (active audio, likely fldigi's device)

  3. Iterate candidates until `pa_simple_new` succeeds

## Session 3: Base64 Parser + Audio Source Index Fix (2026-05-10)

### Problem (User confirmed session 2 fixes still didn't work)
User ran neodigi and provided terminal log. Two issues remained:
1. `rx.get_data` returns `<base64>UA==</base64>` but RX pane empty
2. Waterfall still shows "NO AUDIO INPUT" even after selecting "Default" in settings

### Root Cause #1 (RX Text): `<base64>` tag not parsed in XML-RPC
- `parseValue()` in `FLDigiClient.cpp` handles `<string>`, `<boolean>`, `<int>`, `<i4>`, `<double>`, `<array>` — but **NOT** `<base64>`
- `rx.get_data` returns `value_bytestring` = XML-RPC type `"6"` = `<base64>` wrapper
- Terminal log confirms: raw response has `<base64>UA==</base64>` (that's "P" decoded), but the parser skipped the element → returned empty QVariant
- **Fix:** Added one line:
  ```cpp
  if (tag == QLatin1String("base64"))
      return QByteArray::fromBase64(xml.readElementText().toLatin1());
  ```
  QByteArray is stored in QVariant → `.toString()` on a QByteArray QVariant returns the decoded text.

### Root Cause #2 (Waterfall): Source index mapping mismatch
- `inputDevices()` returns: `[{"", "Default"}, {"src1", "desc1"}, {"src2", "desc2"}, ...]`
- `setAudioDevice(int deviceIdx)` matched `s.index == deviceIdx` directly
- `listSources()` assigns index 0 to first real source
- So selecting "Default" in the audio dialog (deviceIdx=0) matched `s.index == 0` = **first real source**, not PA default
- Similarly, selecting first source (deviceIdx=1) matched second source (s.index=1)
- **Fix:**
  - `setAudioDevice(0)` now means "auto-detect / PA default" (calls `initAudio(nullptr)`)
  - `setAudioDevice(1+)` uses `s.index == deviceIdx - 1` to correct the offset
  - Auto-start in MainWindow uses `setAudioDevice(i)` instead of `setAudioDevice(i - 1)` for the matched device index

## Session 4: PipeWire pactl Fallback for Source Enumeration (2026-05-10)

### Problem
Waterfall audio source selection fails even after index mapping fix. User reports:
- Dialog shows "Disabled (stub waterfall)" and only one other option ("Default")
- Selecting the other option → waterfall reverts to stub mode
- No selection persists

### Investigation
- `listSources()` uses `pa_context_get_source_info_list()` via PA `pa_mainloop` API
- On **PipeWire**, the PA context API may fail silently or return empty results:
  - `pa_mainloop_new()` succeeds
  - `pa_context_connect()` may succeed
  - But `pa_context_get_source_info_list()` may hang, return 0 sources, or error out
  - `pa_context_get_state()` may not reach `PA_CONTEXT_READY` in time
- If `listSources()` returns empty → `inputDevices()` only has `[{"","Default"}]`
  - Combo box: [0: "Disabled", 1: "Default"] — matches user's "only other option"
  - → no real hardware sources selectable
- `setAudioDevice(0)` → `initAudio(nullptr)` → `candidates` is just `[QString()]` (PA default)
- `pa_simple_new(nullptr, ...)` with PA default on PipeWire also fails (returns error)
  - Exact error unknown — need to check terminal for `pa_strerror()` output
- This is a PipeWire-specific PA compatibility issue. `pa_mainloop` + `pa_context_get_source_info_list` doesn't work reliably on all PipeWire versions.

### Fix: pactl fallback for source enumeration
- Added `listSourcesPactl()`: parses output of `pactl list sources short` via `popen()`
  - `pactl` works reliably on both PulseAudio and PipeWire
  - Parses tab-separated columns: index, name, driver, sample_spec, state
  - Filters out monitor sources (name contains ".monitor")
  - Generates human-readable description from source name
- Modified `listSources()`:
  1. Try PA context API first
  2. If returns empty → call `listSourcesPactl()` as fallback
  3. Logs fallback to console: `[Waterfall] PA source API returned empty — falling back to pactl`

## Session 5: Latin1 Encoding + Control Char Filter for Clean RX Text (2026-05-10)

### Problem
User compared neodigi vs fldigi RX outputs side-by-side (files: `neodigirx.txt`, `fldigirx.txt`). fldigi shows clean FLAMP text, neodigi shows garbled text with `�` replacement characters and jumbled data.

### Analysis of neodigirx.txt
```
nRrcoapM �sFtC l 0 s `seonns v=e lSfu
PEMS Ne NY3J<PRO4D9BA6C}MP 2.4
```
vs fldigirx.txt:
```
PROG 18 4D9B>{CA6C}FLAMP 2.2.14
<FILE 27 3086>{CA6C}20260510002537:pa.txt
```

Known fragments exist (`NY3J`, `PRO`, `4D9B`, `A6C`, `MP 2.4`) but jumbled & damaged.

### Root Cause: UTF-8 interpretation of raw bytes
- `rx.get_data` returns base64-encoded raw bytes from fldigi's RX buffer
- Our `<base64>` handler decodes to `QByteArray` correctly
- `QVariant::toString()` on a `QByteArray` calls `QString::fromUtf8()` internally
- Bytes ≥ 0x80 (common in RSID noise, mode-switching artifacts) form **invalid UTF-8** sequences
- Qt replaces invalid sequences with `\uFFFD` (`�`), shifting/corrupting subsequent characters
- Additionally, raw buffer includes control characters (0x00-0x1F) for RSID, modem handshake, etc.

### Fix 1: Latin1 decoding (FLDigiClient.cpp)
```cpp
QString FLDigiClient::getRxData()
{
    if (m_stubMode) return {};
    QVariant result = call("rx.get_data");
    if (result.typeId() == QMetaType::QByteArray) {
        const QByteArray raw = result.toByteArray();
        return QString::fromLatin1(raw);  // ← byte-perfect, no mojibake
    }
    return result.toString();
}
```
`QString::fromLatin1()` maps each byte to its Unicode equivalent 1:1 — bytes 0x80-0xFF become U+0080-U+00FF, no replacement, no corruption.

### Fix 2: Filter control characters (MainWindow.cpp)
Strips non-printable control characters from RX text before display (except `\n`, `\r`, `\t`):
```cpp
for (int i = 0; i < rx.size();) {
    const QChar c = rx.at(i);
    if (c.unicode() < 0x20 && c != '\n' && c != '\r' && c != '\t') {
        rx.remove(i, 1);
    } else {
        ++i;
    }
}
```
This matches fldigi's display behavior — RSID noise, mode-switch artifacts, and protocol framing bytes are hidden.
